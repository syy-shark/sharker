# 文档驱动开发指南

## 代码注释约定

- 每个 `.ts` / `.tsx` 源文件顶部有 **文件级 JSDoc**（中文说明职责 + `@see` 对应本目录或上级架构 `ARCH.md`）。
- **每个导出**的函数、类、常量、interface/type 上方有简短 **JSDoc**（中文：做什么、关键参数/返回值）。
- **非平凡内部函数**（非一行 getter）同样加 JSDoc；函数体内仅在逻辑非常晦涩时写行内注释。
- React 组件在导出函数上方写 JSDoc，或在文件头说明 Props 用途；不写 JSX `map` 回调里的箭头函数注释。
- `tool-definitions.ts`：文件头 + 每组工具一段区块注释即可。
- 改逻辑时 **同步更新** 相关注释。

## 原则

1. **逐层架构说明（强制）**：每一个有源码/配置意义的目录，都必须有一份 **同级架构说明** `ARCH.md`，说明 **本目录下** 的文件夹与文件。见下文「逐层架构说明规范」。
2. **全局索引在 `docs/`**：顶层模块、全局设计文档在 [docs/ARCH.md](./ARCH.md) 登记；`docs/` 内专题文档（架构、能力、路线图等）不替代各目录的同级说明。
3. **改代码必改文档**：增删改同级文件/目录、行为、接口、依赖变化时，同一 PR / 同一次提交更新 **该层** `ARCH.md`（及受影响的上层说明）。
4. **AI 先读后改**：修改某处前，先读 **该目录 `ARCH.md`**（必要时沿父目录向上读）+ [ARCHITECTURE.md](./ARCHITECTURE.md)。

## 逐层架构说明规范

### 核心规则

> **每一层目录都有一份架构说明 Markdown；该文档只写「本目录同级」的文件夹与文件各是干什么的。下一级目录各自再有一份，说明下一级的同级内容。如此递归，直到叶目录。**

- 文件名统一为 **`ARCH.md`**（**A**rchitecture 缩写：A 开头、按名排序靠前、比 README 更好找）。
- **不要**与 `docs/ARCHITECTURE.md` 混淆：后者是 **全系统** 架构专题；前者是 **本目录同级地图**。
- **作用域**：只描述 **当前目录下的直接子项**（同级文件夹 + 同级文件）。不要把孙目录里的文件清单摊在本层写满。
- **递归**：若子项是文件夹，本层 `ARCH.md` 用 **一句话** 说明该文件夹职责，并指向 `子目录/ARCH.md`；子目录内再维护自己的同级清单。
- **中文** 为主；标识符（路径、导出名）保持代码原名。

### 示意

```text
foo/                    ← foo/ARCH.md 说明 bar/、baz.ts、qux.ts …
├── ARCH.md
├── bar/                ← bar/ARCH.md 说明 bar 内的 a.ts、nested/ …
│   ├── ARCH.md
│   ├── a.ts
│   └── nested/         ← nested/ARCH.md 说明 nested 内的 …
│       ├── ARCH.md
│       └── …
└── baz.ts
```

根目录 **`README.md`** 仍作产品入口（怎么装、怎么跑）；`docs/` 专题写跨模块设计；**各业务目录的 `ARCH.md` 负责该层地图**。

### 每层 `ARCH.md` 最少包含

| 段落 | 要求 |
|------|------|
| **标题** | 目录名 + 一句话角色（如 `# tools — 工具执行层`） |
| **职责** | 本目录管什么、不管什么（2～5 句即可） |
| **同级目录** | 表格：`目录名` \| 一句话职责 \| 链到 `./子目录/ARCH.md`（若有） |
| **同级文件** | 表格：`文件名` \| 一句话说明 |
| **可选加深** | 顶层/核心模块可另写：对外接口、依赖、扩展点、关键流程 |

叶目录若文件很少，表格仍要写全同级项；不必硬凑「接口 / 依赖」段落。

### 何时必须新建 / 更新

| 动作 | 文档义务 |
|------|----------|
| 新建有源码意义的目录 | 立刻补 `ARCH.md`，并在 **父目录** `ARCH.md` 的「同级目录」表中加一行 |
| 新增同级文件或子目录 | 更新 **本层** `ARCH.md` 对应表格 |
| 删除 / 重命名同级项 | 同步改本层（及父层若对外名变了） |
| 只改文件内部实现、对外职责不变 | 可不改本层 `ARCH.md`；若职责一句话已过时则改 |
| 行为/策略/IPC 等跨模块变化 | 除本层外，按「全局文档何时更新」表改 `docs/` |

### 豁免（不必写 `ARCH.md` 的目录）

以下目录 **不要求** 架构说明（也不应在文档树里当作业务模块登记）：

- 生成物与依赖：`node_modules/`、`out/`、`dist/`、`*.tsbuildinfo` 所在构建缓存
- 纯二进制/静态资源堆：仅含图片、字体、无逻辑配置的目录（如仅 PNG 的 `resources/icons/`）——若日后加入脚本/配置，再补 `ARCH.md`
- 第三方 vendored 且自带说明的树（若有）以其自述为准，不强制套本规范

**灰色地带**：`scripts/`、`public/`、`resources/` 等若含可维护脚本或需协作说明，**应当**有 `ARCH.md`。

### 与全局文档的分工

| 层级 | 写什么 |
|------|--------|
| 根 `README.md` | 产品是什么、怎么跑、顶层目录一览 |
| `docs/*` | 跨模块架构、能力、路线图、安装、UI 风格等专题 |
| 各目录 `ARCH.md` | **该层地图**：同级文件/文件夹说明 +（核心模块）接口与扩展点 |

父层 **不要** 复制子层完整文件表；子层细节以下层 `ARCH.md` 为准。

## 顶层 / 核心模块 `ARCH.md` 建议加深

对 `agent/`、`tools/`、`src/`、`electron/`、`shared/`、`providers/` 等入口模块，在「同级清单」之外建议保留：

- **对外接口**：导出函数、IPC、Props
- **依赖**：依赖谁、被谁依赖
- **扩展点**：以后要加功能改哪里
- **关键流程**（可选）：如 Turn 管线示意

## 全局文档何时更新

| 变更类型 | 更新文档 |
|----------|----------|
| 新工具 / 改 Harness 策略 | `agent-capabilities.md` + `agent/ARCH.md`（及 `tools/` 相关层） |
| 内联可视化行为 / 套壳 | `inline-demo-spec.md` + `agent/loop.ts` prompt + `InlineDemo.tsx` |
| 新 IPC / 存储格式 | `ARCHITECTURE.md` + `electron/ARCH.md` |
| 新 UI 页面/流程 | `src/ARCH.md`（及 `src/components/` 等受影响层）+ 必要时 `ui-style.md` |
| 外观 / 主题 / 材质 | `ui-style.md` + `src/ARCH.md` |
| 新里程碑 / 已拍板决策 | `roadmap-harness.md` |
| 新顶层模块目录 | 根 `README.md` 目录表 + [docs/ARCH.md](./ARCH.md) 模块表 + 该目录 `ARCH.md` |

## 给 AI 的提示

在 Sharker **用户工作区**里，项目规则写在仓库根 `AGENTS.md` / `AGENTS.override.md`，或 `<工作区>/.sharker/AGENTS.md`（`/init` 在当前目录生成脚手架；全局规则在 `~/.sharker/AGENTS.md`）。

在 **Sharker 源码仓库**里：

1. 以 `docs/` 专题 + **逐层** `ARCH.md` 为准。
2. 进入某目录改代码前，先读 **该目录** `ARCH.md`；缺则先按本规范补全再改，或在同次提交中补上。
3. 新增目录/文件时，默认义务是 **本层 `ARCH.md` + 父层同级表**，不要只改代码。
